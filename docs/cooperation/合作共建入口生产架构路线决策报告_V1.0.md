## 二、决策边界

本轮仅决定生产路线应如何签认，不修改 DNS，不创建生产数据库，不写入生产数据，不合并 `main`，不开放正式入口。

已知基线：

- 正式主域 `https://xintuozhiwuye.com` 当前由 Vercel 项目 `judao-club` 提供，首页可访问；
- `/cooperation` 与 `/cooperation/register` 当前为 404；
- Vercel + Supabase Staging 已完成数据库、Auth、TOTP MFA、RBAC、审计、迁移与恢复验证；
- Production 数据库、Auth、Secrets、备份、具名管理员和生产验证均未建立；
- 合作登记包含联系人、电话、微信、邮箱等个人信息，数据地域与供应商边界必须由具名数据/合规负责人书面批准。

## 三、方案 A：Vercel + Supabase 过渡生产

```text
xintuozhiwuye.com
→ Vercel judao-club（Next.js）
→ Supabase Production（PostgreSQL + Auth + TOTP MFA）
```

| 维度 | 判断 |
|---|---|
| 上线速度 | 最快；与已验证 Staging 技术栈一致，可复用应用、schema、迁移和安全测试 |
| 运维成本 | 初期较低；托管应用、数据库、身份和备份，但需采用满足生产备份/PITR要求的付费能力 |
| 数据地域 | 需选择可用境外区域；当前 Staging 位于东京，不能自动推定为获批 Production 地域 |
| 企业客户接受度 | 对国内机构客户可能产生数据地域、供应商、访问稳定性和采购审查疑问 |
| 合规工作 | 若向境外提供个人信息，需要由合规负责人判断适用义务、完成告知/同意及其他法定条件，不能仅以技术加密替代 |
| 后续迁移成本 | 需要从 Supabase Auth、PostgreSQL、Secrets、备份和 Vercel Runtime 迁到国内体系；身份迁移尤其需要重新绑定或安全重建 MFA |
| 路径接入 | 当前主域已在 Vercel，可通过同一 Next.js 应用接入四个路径，通常无需 DNS 改动 |
| 主要风险 | 把“最快上线”误作“合规已批准”；形成过渡架构长期化；跨境访问与供应商锁定 |

方案 A 只有在数据/合规负责人对数据处理地域和供应商形成书面意见、总架构师批准“过渡期限与退出条件”、三类管理员真实具名后，才能作为生产候选。

## 四、方案 B：国内云正式生产

建议逻辑架构：

```text
中国内地 DNS / CDN / WAF
→ 同一正式 Next.js 应用（官网 + /cooperation）
→ 国内 PostgreSQL 高可用数据库
→ 国内身份服务或经批准的自有身份层
→ KMS / Secrets / 日志 / 告警 / 备份 / PITR
```

可选产品应在 No.030-B 采购/技术评审中确定；本报告不把“阿里云”自动指定为唯一供应商。可评估阿里云、腾讯云或满足同等控制要求的国内云。

| 维度 | 判断 |
|---|---|
| 合规 | 有利于把服务和个人信息处理落在中国内地；仍需完成隐私、授权、备案、最小权限和安全治理，国内部署本身不等于自动合规 |
| 数据控制 | 云账号、数据库、KMS、备份、日志和应急权限可纳入项目主体的企业账号与责任体系 |
| 长期自主能力 | 可形成统一主站、合作入口和后续平台能力的长期生产底座 |
| 建设成本 | 高于方案 A；需要建立运行环境、身份、监控、备份、发布和运维值守能力 |
| 迁移难度 | 应用代码可迁；Supabase Auth/TOTP 不应直接复制 Secret，管理员需在新身份体系重新安全建档和绑定 MFA |
| 备案与域名 | 使用中国内地服务器对外提供互联网信息服务前，应完成适用的 ICP 备案/接入要求；如使用中国内地 CDN，同样需核对备案要求 |
| 路径接入 | 若拒绝长期反向代理按路径拼接，又坚持根域同路径，则官网与合作模块必须迁为同一生产发布单元，再一次性切换根域 |
| 主要风险 | 责任人和运维能力未建立前仓促建云；备案周期；身份方案重建；双写或多源数据 |

## 五、比较结论

| 决策因子 | 方案 A | 方案 B |
|---|---|---|
| 最短上线时间 | 优 | 中/慢 |
| 国内访问与长期品牌 | 条件满足 | 优 |
| 个人信息地域可解释性 | 需跨境专项评估 | 较清晰，但仍需合规签认 |
| 与当前 RC 一致性 | 优 | 需适配和复验 |
| 长期自主运维 | 中 | 优 |
| 一次性建设工作量 | 低 | 高 |
| 二次迁移风险 | 高 | 低 |

## 六、推荐决定

```text
recommended_production_path = B_DOMESTIC_CLOUD
current_stage = 继续保留 Vercel + Supabase 作为 Staging 与迁移参照，不转为正式可写生产
future_migration = 不适用二次迁移；No.030-B 直接建立国内 Production 候选并执行等价验证
```

理由：平台主要服务中国大陆用户，正式入口收集个人信息，且既有 No.027/No.028 已把国内生产环境作为长期方向。直接采用方案 B 可避免短期生产后再次迁移身份、数据库、备份和 COL 权威源。

该推荐会带来一个明确影响：为保持 `https://xintuozhiwuye.com/cooperation` 且不采用长期反向代理拼接，应把现有官网与合作模块作为同一 Next.js 生产单元迁入国内云，而不是只迁 `/cooperation`。

若项目负责人基于时限坚持方案 A，必须形成例外决定，至少写明：有效期、数据地域意见、供应商批准、退出日期、迁移预算、单一写入源和到期复核人；未形成例外批准前仍按方案 B 推进。

## 七、未来实施阶段

1. No.030-A：总架构师、Project Owner、数据/合规负责人签认路线与责任；
2. No.030-B：建立隔离的国内 Production 候选资源，不开放公网写入；
3. 迁移 Next.js 应用并完成数据库、身份、Secrets、备份和安全等价验证；
4. 完成备案/接入、域名切换预案和回滚演练；
5. No.030-C：最终数据迁移与 Go/No-Go 复核；
6. 获得具名批准后才能执行生产发布。

## 八、风险与控制

| 风险 | 控制 |
|---|---|
| 国内云建设时间不可控 | 先完成账号、备案和资源责任人，再排生产窗口；Staging 不删除 |
| 官网与合作模块迁移范围扩大 | 使用同一 RC、分阶段预发布、全站回归与可回退 DNS 计划 |
| 身份能力不等价 | 以 AAL2、个人账号、RBAC、Session 撤销和审计为验收，不以产品名称为验收 |
| 历史数据丢失或双写 | T-0 停写、单一权威源、哈希导出、COL 续接、禁止号码回收 |
| 备案或合规未完成 | 未取得证据不得开放正式入口 |
| 责任归属空白 | 责任表未具名即保持 NO-GO |
