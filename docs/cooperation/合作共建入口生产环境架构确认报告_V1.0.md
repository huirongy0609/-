## 三、候选生产架构

### 3.1 过渡生产候选

在保持当前主域和最小迁移风险的前提下，短期候选架构为：

```text
xintuozhiwuye.com
        ↓ Vercel Edge / TLS
judao-club Production（Next.js 15.5.23 / Node.js 24.x）
        ├── /cooperation/register
        ├── /cooperation/success
        ├── /cooperation/admin
        └── /api/cooperation-*
                     ↓ TLS + CA verification
独立 Supabase Production Project
        ├── PostgreSQL cooperation_* schema
        ├── Auth + TOTP MFA
        └── 备份 / PITR / 审计
```

该方案与已经验证的 RC 技术栈最接近，但属于境外托管过渡方案。只有数据/合规负责人对个人信息处理地域、跨境访问和供应商条款形成书面批准后才能采用。

### 3.2 长期正式目标

既有 No.017、No.027 和 No.028 将面向中国大陆用户的长期正式目标定义为国内云：

```text
阿里云云解析 / 国内接入层
→ SAE 标准 Node.js 容器
→ RDS PostgreSQL 高可用版
→ 国内身份、KMS、SLS、监控与备份
```

如总架构师坚持国内生产基线，本次 Vercel/Supabase RC 只能作为技术预发布证据，不能直接升级为正式生产。两个方向必须择一签认，禁止形成两个同时可写的生产系统。

## 五、数据层确认项

推荐创建全新 Production PostgreSQL，不允许把 Staging 项目改名后直接作为生产：

- 与 Staging 使用不同项目、数据库密码、API keys、Auth 租户和管理员；
- 使用同一版本化 schema `db/cooperation/001_initial.sql`；
- 六张合作表保持唯一约束、外键、COL 原子序列和追加式审计；
- 生产网络访问、SSL enforcement 和 CA 校验必须启用；
- Production 数据不得回流到 Staging，测试只使用脱敏或专门批准的数据；
- 备份目标为 `RPO ≤ 15 分钟`、`RTO ≤ 2 小时`。

若采用 Supabase，Free Plan 不满足本项目正式备份和不暂停要求；至少应使用具备每日备份的付费计划，并根据 RPO 启用 PITR，同时保留离站加密逻辑备份。正式选择及费用必须批准后执行。依据：[Supabase Database Backups](https://supabase.com/docs/guides/platform/backups)。

## 六、身份层确认项

生产身份方案必须为：

```text
具名个人账号
→ 密码/身份提供方验证
→ 每人独立 TOTP MFA
→ AAL2 Session
→ cooperation_admin_user 角色映射
→ 服务端逐接口授权
→ 追加式审计
```

禁止共享管理员账号、共享 TOTP Secret、仅隐藏后台 URL、把既有知识后台 Basic Auth 直接复用为合作后台身份。

## 七、域名与路径

正式路径冻结为：

```text
https://xintuozhiwuye.com/cooperation
├── /register
├── /success
└── /admin
```

要求：

- `/cooperation` 必须提供合作共建说明页或 308 到 `/cooperation/register`；当前 RC 为 404，属于发布 P0。
- `/admin` 不进入导航、sitemap 和搜索索引；未认证跳登录，API 返回 401。
- `/success` 不能泄露联系人信息或允许猜测其他 COL。
- `.cn`、`.net` 只承担经批准的跳转，不承载第二套可写表单。
