# 合作共建入口生产路线最终确认记录 V1.0

## 一、记录结论

Codex No.030-A-确认版任务单已明确生产路线方向：

```text
production_route_direction = B_DOMESTIC_CLOUD
staging_route = VERCEL_PLUS_SUPABASE_STAGING
direction_recorded = true
human_signoff_complete = false
production_path_approved = false
```

本记录将国内云固化为待签认的唯一正式生产方向。由于尚无具名总架构师、Project Owner、数据/合规负责人签名或可追溯批准证据，不能把“任务单明确方向”替代“真实人工签认”，当前仍不构成 Production 资源创建或发布授权。

## 二、正式生产路线

正式生产采用中国内地云环境，目标逻辑架构为：

```text
xintuozhiwuye.com
→ 中国内地 DNS / CDN / WAF / HTTPS
→ 统一 Next.js 应用（官网 + /cooperation）
→ 中国内地 PostgreSQL 高可用数据库
→ 具名管理员身份 + MFA + RBAC
→ KMS / Secrets / 审计 / 监控 / 备份 / PITR
```

生产数据库、身份租户、Secrets、备份和日志必须与 Staging 物理或项目级隔离。正式数据只允许一个权威写入源。

## 三、Staging 路线

继续保留：

```text
Vercel Preview
+ Supabase Staging
```

用途仅限：

- 开发验证与代码评审；
- 发布前功能、安全和权限测试；
- schema、历史数据与 COL 迁移演练；
- 故障注入、备份恢复和回滚演练；
- 国内 Production 候选的对照验证。

明确禁止：

- 作为长期正式生产或正式数据权威源；
- 接收对外正式合作登记；
- 使用 Production 数据库、管理员、Secrets 或完整个人信息副本；
- 与国内 Production 同时开放写入；
- 把 Staging 通过结果直接替代 Production 环境实测。

## 四、当前选择原因

1. 平台主要服务中国大陆用户，正式合作表单处理联系人、电话、微信和邮箱等个人信息；国内生产有利于形成更清晰的数据地域和责任边界。
2. 既有 No.027、No.028 和 No.030-A 已把国内云定义为长期目标，直接建设可避免过渡生产后再次迁移数据库、身份和备份体系。
3. 国内云便于把域名接入、备案、云账号、数据库、KMS、日志和应急权限纳入同一企业治理链。
4. 国内多运营商访问、客户采购审查和长期品牌入口更适合由中国内地生产环境承担。
5. 现有 Vercel/Supabase RC 已证明应用链路可行，继续作为 Staging 可保留研发效率，无需废弃已完成验证。

国内部署并不自动等于合规。仍必须完成适用的 ICP/公安备案、个人信息告知与授权、最小权限、审计、备份恢复和具名责任人确认。

## 五、数据安全考虑

| 控制面 | 生产要求 |
|---|---|
| 数据地域 | Production 数据库、备份、日志和身份数据默认位于批准的中国内地地域 |
| 单一权威源 | T-0 后只有国内 Production 可写；旧 D1、Sites 和 Staging 保持停写 |
| 网络 | 数据库私网访问；公网入口经 HTTPS/WAF；管理面限制来源并强制 MFA |
| 身份 | 每人独立账号、TOTP MFA/AAL2、服务端 RBAC、Session 撤销 |
| Secrets | KMS/Secret Manager 托管，Staging/Production 分离，双人复核和轮换 |
| 备份 | 自动全量 + 日志/PITR + 加密离站备份；按 RPO/RTO 演练 |
| 审计 | 管理、导出、迁移、角色、MFA、拒绝访问和恢复操作只追加留痕 |
| 数据最小化 | 只收集已批准字段；日志、监控和错误页不得出现个人信息或凭证 |

## 六、迁移策略

```text
保留已验证 Staging
→ 国内 Production 候选建资源
→ 应用与 schema 等价部署
→ Auth/RBAC/MFA 在国内体系重新建档
→ 两轮迁移与恢复演练
→ T-24 冻结
→ T-0 D1 停写、导出、校验、导入与 COL 续接
→ No.030-C Go/No-Go
→ 获批后根域切换与正式开放
```

- 不迁移 Supabase 测试身份、TOTP Secret、Session、测试审计或 Mock 数据；
- 历史正式 COL 不得重置、回收或重新编号；
- 迁移使用版本化脚本、导出哈希、源/目标数量和关系校验；
- 官网与合作模块作为同一构建单元迁移，以保持根域子路径且避免长期反向代理拼接；
- Staging 在生产稳定观察期结束前保留，但始终不可成为第二生产写入源。

## 七、技术债处理

| 技术债 | 处理决定 | 截止门槛 |
|---|---|---|
| `/cooperation` 在 RC/正式域名 404 | 增加 200 说明页，优先于 308 | 国内 Production 候选验收前 |
| 已验证代码未进入 release/main | 先提升到 release；No.030-C Go 后才允许合并 main | 正式发布前 |
| Supabase Auth 与国内身份不等价 | 以 MFA、RBAC、Session、审计验收；重新安全建档管理员 | Production 安全测试前 |
| 本地/境外运行假设 | 容器化并验证 Node.js Runtime、只读文件系统、健康检查和优雅停机 | 候选构建前 |
| 备份仅在 Staging 验证 | 国内数据库执行真实 PITR/恢复演练 | `rollback_ready=true` 前 |
| 云厂商锁定 | PostgreSQL 标准 schema、可导出备份、应用层权限接口、不可变容器镜像 | Production 建设时 |
| 监控与值守缺口 | 建立日志、指标、告警、联系人和事件流程 | 开放入口前 |

技术债不得以“上线后再说”无限延期。任何影响个人信息、权限、COL、备份或回滚的债务均为发布阻断项。

## 八、退出与变更机制

未来若更换云厂商或变更为其他生产路线，必须：

1. 形成新的架构决策记录；
2. 证明数据导出、身份重建、COL 连续和审计保留方案；
3. 完成目标环境两轮迁移/恢复与安全测试；
4. 禁止双主写入；
5. 由总架构师、数据/合规负责人和 Project Owner 重新批准。
